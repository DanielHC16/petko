# Guest browsing and verified product reviews

Status: implemented, reviewed, and locally verified; PR and deployment pending. Baseline: `main` at `f77857e` on 2026-11-14. This document is the implementation handoff and release checklist.

## Goal and accepted behavior

Guests can browse, search, filter, select variations, and read product reviews without an account. The login screen has **Browse without an account**. Guest purchase/cart actions explain that an account is required and link to the existing Google sign-in/sign-up flow. No anonymous cart is created, and no order or cart mutation runs automatically after authentication. Cart, checkout, orders, profile, and all admin screens remain protected.

Only the owner of an order whose receipt the customer has confirmed can review its purchased products. Admin-reported delivery alone is insufficient. There is one editable review per customer per purchased product ID (SKU); repeat purchases do not add rating weight. Reviews appear immediately. Admins can hide/unhide abuse but cannot edit a customer's rating or text. Owners can edit or withdraw their reviews. Hidden state survives owner edits and reposts.

Each review has a required integer rating of 1–5 displayed as paws and an optional plain-text comment of at most 2,000 characters. No photos, attachments, replies, helpful votes, or separate store/service reviews. Sibling-variation reviews are combined on the product family detail with the purchased variation identified. Everyone, including guests, can read visible reviews and their aggregate rating. Owner/admin information is served separately from the public response.

Defaults accepted for implementation: public author display is first name plus last initial (or `Petko customer` when unavailable); never expose email, account/order/item identifiers, or avatar URLs. Account deletion removes authored reviews via cascade, consistent with the existing promise to delete the profile and identifying content. Existing completed purchases qualify; no historical review backfill or fabricated ratings. Simulated cashless orders qualify on confirmed receipt exactly like COD because they remain normal fulfillable orders.

## Decision and tradeoffs

Extend the current modular monolith: one new Nest reviews module with controller → service → repository, private PostgreSQL functions for eligibility/read/write transactions, and one frontend reviews feature. Keep guest catalog pages within the same layout while nesting only private routes beneath the existing guard. This avoids a parallel guest storefront and preserves cart isolation.

A browser-only review store would not enforce verified ownership or survive devices. Direct client writes with broad RLS would duplicate eligibility/aggregation logic and make moderation easier to bypass. Use service-role-only tables/functions behind bounded Nest DTOs, exposing only deliberate public projections. One review per order item would overweight repeat buyers; the confirmed one-per-customer/SKU choice avoids that.

## Data model and transaction rules

Create idempotent `petko-be/supabase/migration-010-guest-browsing-product-reviews.sql` and matching schema definitions. Add `public.product_reviews`:

- `id uuid primary key`, `user_id uuid not null references public.users(id) on delete cascade`, `product_id uuid not null references public.products(id) on delete restrict`.
- `order_item_id uuid not null references public.order_items(id) on delete restrict`: the verified purchase source, never public. All three relationships are checked in the creation transaction. A review does not duplicate shipping, email, author name, or product snapshots.
- `rating smallint not null check (rating between 1 and 5)`, `comment text not null default '' check (char_length(comment) <= 2000)`; normalize with trim and validate text lengths server-side and in SQL.
- `is_hidden boolean not null default false`, `withdrawn_at timestamptz null`, `version integer not null default 0`, `created_at/updated_at timestamptz not null default now()`; unique `(user_id, product_id)`.
- Partial visible index `(product_id, created_at desc, id desc) where not is_hidden and withdrawn_at is null`; supporting owner/purchase indexes if not already covered.
- RLS enabled, no anon/authenticated policies, all table privileges revoked from PUBLIC/anon/authenticated; service role only. Every function fixes `search_path = ''`, qualifies objects, revokes execution from PUBLIC/anon/authenticated, and grants only service_role.

Private function contracts (names may be consistently adjusted before implementation, not duplicated):

1. `petko_product_reviews(p_product_id uuid,p_page integer,p_limit integer) returns jsonb`: resolve an active selected SKU's exact current family; return only nonhidden/nonwithdrawn rows and safe author labels. Include out-of-stock/inactive siblings in family aggregation so stock depletion does not erase real reviews. An inactive selected root returns 404, matching the frontend catalog's active-only RLS; owner purchase context remains available for historical inactive purchased items. Bound page/limit and order deterministically by `created_at desc,id desc`. Calculate count/average/distribution and page from one statement snapshot; null average and zero count for no reviews. No cached/materialized aggregate to drift after moderation/deletion.
2. `petko_review_context(p_user_id uuid,p_product_id uuid,p_order_id uuid default null) returns jsonb`: owner-only purchase eligibility plus that customer's existing slot. If an order is supplied, require ownership and that SKU in the specified order. Otherwise choose a deterministic confirmed purchased item. Return a reason when no completed purchase; never expose another customer's record. Owner can view a hidden review and its status; that does not republish it.
3. `petko_save_product_review(p_user_id uuid,p_product_id uuid,p_order_item_id uuid,p_rating integer,p_comment text,p_expected_version integer default null) returns jsonb`: lock the owner, then qualifying order, then review row. Verify matching owner/product/item, `delivery_confirmed_at is not null`, and noncancelled status inside the same transaction. Create once when expected version is null and no slot exists; an existing slot yields safe 409 with refresh instruction. Edit/repost only at matching version; increment version and set `withdrawn_at=null`, preserving `is_hidden`. A unique violation from concurrent initial posts maps to 409. Return the private OwnReview projection atomically, avoiding a second read after the committed write. Never take user ID, moderation state, verified status, or author name from client data. No stock/order/cart mutations.
4. `petko_withdraw_product_review(p_user_id uuid,p_review_id uuid,p_expected_version integer) returns boolean`: owner-only, version checked, set `withdrawn_at`, increment version. A tombstone retains the unique slot and moderation state so withdrawal/repost cannot bypass a hidden decision. Withdrawn content contributes nothing to public list/count/average; owner context can show its draft. Auth/profile deletion hard-deletes it by cascade. Do not claim this owner action permanently erases the database row.
5. `petko_moderate_product_review(p_review_id uuid,p_is_hidden boolean,p_expected_version integer) returns jsonb`: admin-authorized Nest route only, check version, update flag/version/time and atomically return OwnReview. No text/rating modification accepted. `petko_admin_product_reviews(p_page integer,p_limit integer,p_visibility text)` returns the bounded moderation list. Admin lists include published/hidden and withdrawn status; do not expose withdrawn text publicly.

Use a stable lock order: owner → order → review for owner mutations. Existing account deletion holds user/orders locks, so a review either commits before the account cascade or fails cleanly afterward. Moderation locks only review and never subsequently owner/order; this avoids reverse lock ordering. Neither creation nor edits change the qualifying order or tracking version. Keep all privacy/admin-lockout/account-deletion protections in migration 008 untouched.

## HTTP contracts

All responses retain `{success:true,data:...,message:''}`. Route parameters use UUID pipes, all bodies/query fields use DTO validation, extra fields are rejected, private mutations bind the authenticated actor. Rating must be integer 1–5; comment defaults to empty and is at most 2,000 after normalization; page 1–100000 and limit 1–50 (default 10). Do not silently coerce malformed ratings. Return safe 400 validation, 401 no session, 403 nonadmin moderation, 404 missing/not-owned records, 409 stale/duplicate/ineligible writes. Log raw database details only server-side.

- **Public `GET /api/products/:productId/reviews?page=1&limit=10`** → `{reviews:PublicReview[],summary:{average_rating:number|null,total_reviews:number,ratings:{1:number,2:number,3:number,4:number,5:number}},page,limit,total,totalPages,scope:'family'|'product'}`. `PublicReview` contains `id,product_id,product_name,variant_label,author_name,rating,comment,created_at,updated_at`. `product_id` is a public catalog identifier. It never contains customer/order/purchase IDs, full name, email, shipping, avatar, moderation notes, or hidden content. This route is unguarded; do not introduce optional-auth failure for public reads.
- **Authenticated `GET /api/products/:productId/reviews/me?order_id=<optional UUID>`** → `{eligible:boolean,reason:'eligible'|'purchase_required'|'receipt_required',order_item_id:string|null,review:OwnReview|null}`. `OwnReview` adds `version,is_hidden,withdrawn_at` to relevant public fields. The purchase ID is private and only used to bind the owner's editor to verified evidence. A valid but unowned order returns 404. The order page passes its order ID; product detail omits it.
- **Authenticated `POST /api/products/:productId/reviews`** → own review; body `{order_item_id,rating,comment?,expected_version?}`. Absent expected version means initial create only; present version means editing/reposting the customer's existing slot. Server derives actor. A lost-success retry loads `/me` rather than inventing a new review; no duplicate aggregate weighting.
- **Authenticated `DELETE /api/reviews/:id?expected_version=N`** → `{removed:true}` meaning withdrawn from public. Owner only. Do not accept a target user ID.
- **Admin `GET /api/reviews/admin?page=1&limit=20&visibility=all|visible|hidden`** → bounded list plus pagination, product label, safe author label, body/rating, hidden/withdrawn state and version. Declare static `admin` before ID routes. Preserve existing admin role guard semantics.
- **Admin `PATCH /api/reviews/:id/visibility`** → admin item; body `{is_hidden:boolean,expected_version:integer}` only. Owner editing a hidden review returns success with a clear owner-only hidden notice; it remains excluded publicly.

An optional `PRODUCT_REVIEWS_ENABLED` backend configuration boolean (default true) is the emergency feature switch. When false, review routes return a safe 503 and the frontend shows a contained unavailable/retry state; catalog, checkout, account, and fulfillment keep working. Verify migration before releasing its default-enabled consumers. No customer-facing technical flag text.

## Risks, compatibility, rollback

Immediate publication can expose abusive text until admins hide it; bounded plain text and real confirmed purchases limit the input surface, and moderation is part of this release. Render text as React text, never HTML. Existing firewall throttling remains the rate-control layer; do not add ineffective per-instance in-memory throttling. Only a verified purchase establishes the badge; client claims never do.

Family membership currently uses mutable exact parent names with no stable family table. Preserve that contract instead of introducing a catalog migration. Purchased SKU labels distinguish variants. Existing historic orders can qualify only while still linked to their signed-in owner; anonymized history never grants eligibility to a new account with the same email. Existing products/orders are not rewritten or reseeded.

The migration is additive except replacing the analytics function with its expanded public-path allowlist. Retain all review tables and data on application rollback. Emergency disable the review module via the backend flag, or restore the previous Vercel deployment; public catalog routes can be reverted independently if necessary. Do not drop tables, restore old checkout/tracking/deletion functions, or republish hidden content as rollback. Review cascade follows a requested real account deletion and is irreversible; test only with isolated fixtures.
