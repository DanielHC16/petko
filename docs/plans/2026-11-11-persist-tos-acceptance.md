# Persist TOS acceptance: design

Goal: once a customer or admin explicitly agrees, their account remembers it across logins, browsers, and devices. Keep the existing terms and scroll-to-agree interaction; add no versioning, dependencies, or new legal text.

## Context and decision

Acceptance currently lives only in localStorage (`petko-fe/src/store/tos.store.ts:18`), and the OAuth callback opens a delayed modal from that flag (`petko-fe/src/features/auth/auth-callback.tsx:29`). Worse, footer Close calls the same handler that records acceptance (`petko-fe/src/components/layout/AppLayout.tsx:207`, `petko-fe/src/features/auth/tos-modal.tsx:48`). These flags cannot reliably prove an agreement and must not be backfilled. Existing accounts may see one final prompt after this release.

Options: retain browser storage (cannot satisfy cross-device behavior); put acceptance in auth metadata (adds a second profile source); or add a boolean to the existing users profile. Choose the profile boolean: the authenticated profile already comes from `GET /users/me` (`petko-be/src/modules/users/users.controller.ts:29`) and `AuthGuard` (`petko-be/src/common/guards/auth.guard.ts:59`). No unresolved product blocker; backend acceptance is one-way, with no reset endpoint.

## Exact contract and invariants

- Add `public.users.tos_accepted boolean not null default false`. Existing and new users default false. Update profile projections and required BE/FE `UserProfile` types; preserve effective-admin computation and existing contracts.
- `POST /api/users/me/tos-acceptance`, `AuthGuard`, no admin restriction. Strict DTO body `{ "tos_accepted": true }` using boolean validation and equality to true. Reject false, missing/invalid values, unknown fields, and caller-supplied user IDs. The target comes exclusively from the authenticated user; a retry sets the same boolean true. Return `{ "success": true, "data": { "tos_accepted": true }, ... }` through the existing interceptor. No full profile response that could overwrite role changes. Missing user or DB failure produces a safe standard error.
- Put the new service-role acceptance update in a focused `UsersRepository`, called through the existing users service, following the project's controller/service/repository rule. Leave legacy user queries unchanged. Update only the acceptance column, scoped to the authenticated UUID. Retain RLS and the existing client update restriction to display fields (`petko-be/supabase/security-patch-001-lock-user-role.sql:27`). No browser role may write acceptance directly, nor gain role-update privileges.
- The server boolean is the source of truth. Remove the callback timer/localStorage acceptance reads and writes. Derive the mandatory prompt in one profile-driven place in AppLayout (or a small feature hook/component), once profile and session identities match. Accepted users still open and close read-only terms from the footer; closing read-only terms never sends acceptance. Unknown/unloaded profiles never count as accepted.
- Accept only after the existing scroll requirement, disable duplicate clicks while saving, keep the modal open until success, and show an inline error with retry on failure. Bind a save to the exact account/token at the click. The shared Axios interceptor awaits the current session and overwrites Authorization (`petko-fe/src/lib/axios.ts:14`), so use a feature-local HTTP helper with the captured Bearer token and same env-driven API base; do not redesign global auth. Capture errors must remain in the modal rather than redirecting a newly switched account.
- Abort/ignore responses and local saving/error state after sign-out, account changes, or unmount. A save for A cannot mark B accepted or dismiss B's prompt. Preserve confirmed true for the same user against an older in-flight profile response containing false (acceptance is monotonic); never carry acceptance into another account. Cover this explicitly rather than relying only on a late-response ID check.
